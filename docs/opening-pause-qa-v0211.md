# v0.21.1 開場暫停修正

基準為v0.21.0、提交b9c67a89fb07d677aafd7d589a32a14bd0ba135b。此前失敗快照顯示前景、倒數已暫停、AudioContext仍running但總音量0；未保存當次完整觸發事件，因此不能把本輪故障注入視為已證明歷史偶發事件的唯一來源。

## 已重現的誤判路徑

`Sound.update`原本以「距離上次音訊時鐘變化超過一秒」判定停滯，沒有區分這段時間是否持續取樣。開場若有長幀／取樣空窗，恢復後第一筆時鐘仍相同便呼叫`interrupt("clock-stalled")`，清除聲源、靜音，接著由主程式的`onInterruption`暫停倒數。單一恢復讀值不能證明整個空窗期間都持續停滯。

本輪先用測試層記錄中斷原因、頁面狀態、音訊時鐘與牆鐘；12次正常／CPU節流開場沒有捕捉自然偶發。接著建立可控制的回歸：讓完整開場取得基準時鐘，在測試層暫停RAF取樣1600ms，恢復的第一個回呼保留舊時鐘，之後恢復Chrome原生時鐘。單人及雙人都在舊版觸發`clock-stalled`並意外暫停；修正後以相同條件比較。這是故障注入，並非聲稱量測到真實音效硬體在該次測試停止。

修正後的最終回歸測例亦回頭套用原版`audio.ts`驗證：兩項開場測試均失敗，再恢復修正來源。沒有延長等待、跳過檢查或自動按「繼續」來掩蓋暫停。

## 修正

- 保存上次實際取樣時間。至少一秒的取樣空窗後，對同一個未前進時鐘只允許一次重新建立觀察基準；必須真正觀察到時鐘前進，才能重新取得下一次空窗寬限。
- 連續取樣超過一秒仍未前進，保留`clock-stalled`清理與暫停。每秒才一幀的持續低幀率也不能反覆重設基準、永久逃過監測。這項邊界由獨立審查指出，已補失敗測例後修正。
- 恢復音訊時重設觀察狀態。背景、AudioSession、context狀態及裝置事件仍走既有的立即中斷路徑，並保留使用者手勢恢復、淡入、音量與靜音偏好。

不改倒數時間、120Hz物理、引擎5、特性1、能力值、計分、戰績或重播格式。舊v1–v4凍結引擎保留。

## 回歸與界線

- `tests/audio-clock.test.ts`：虛擬牆鐘與最小音訊圖檢查1000／1600ms空窗、時鐘前進後下一次空窗、正常頻率下真正停滯，以及每秒才一幀的持續停滯。加入一般核心測試，因此GitHub每次push／PR會執行。
- `tests/e2e/opening-pause.spec.ts`：Chrome完整單人／雙人開場，控制RAF空窗及首次時鐘讀值；不能意外暫停，且必須直接進入戰鬥。GitHub安裝Playwright鎖定版本的Chromium並執行同一測例；本機仍使用Chrome。Windows版WebKit沒有提供AudioContext（含webkitAudioContext），因此不將此音訊故障注入列入WebKit覆蓋，也不以替代假音訊圖冒稱通過。
- 沿用原生Chrome音訊圖測試，檢查真停滯、裝置／通話／背景中斷與恢復、單份配樂、靜音及音量偏好；舊戰績以原引擎重播核對。
- GitHub沿用完整66,708場平衡、核心測試及正式建置；不改門檻、種子或物理來讓檢查通過。

目前仍無iPhone可供實機驗收。Chrome／Chromium音訊、WebKit既有操作、故障注入及桌面重複開場結果不能代替實際藍牙、耳機、來電、鎖屏或熱度測試。網頁端音訊狀態正常也不代表已確認實際喇叭有聲。
