# v0.20.6 P0 裝置與長時間驗收

本輪P0分為程式修正、桌面自動化與iPhone實機驗收。**實機仍待執行，不能把自動化或故障注入當成已通過藍牙、耳機拔插、來電、鎖屏或溫度測試。** 物理、能力值、計分、戰績與重播格式均未變。

## 已修正

- 暫停後原本仍每幀渲染，原生WebGL呼叫量測在800ms增加4,214次。現在暫停及背景停止重複繪製；尺寸變更、模型／貼圖變更和WebGL恢復會標記補畫，繼續後正常渲染。
- 已無聲的暫停仍每幀對持續振盪器送出音量／頻率排程，原生AudioParam量測800ms增加200次。現在當模式、待載入和聲源均已靜止時略過重複更新；原有淡出與聲源清理仍完成。
- 紀錄採固定1001格的幀間隔直方圖、最多30筆每分鐘FPS摘要、最近60筆音訊事件。沒有逐幀無限儲存陣列、新輪詢計時器或新增依賴。

## 手機操作流程

1. 開啟公開遊戲，確認版本0.20.6。從「♫ 配樂 → 裝置檢查」或「遊戲規則 → 裝置檢查」進入。
2. 按「開始新紀錄」，再進入對戰；在對戰中開啟檢查會暫停，關閉後按「繼續」。開始新紀錄會清除這次原有的統計及勾選。
3. 保持相同的遊戲與系統音量，分別測試下表。可用「恢復音訊」重試與「測試聲音」送出短音；送出不等於耳機真的有聲，依實際聽感勾選。
4. 每項完成後在檢查頁選「通過」或「異常」；沒有設備或未實測時保留「未測試」。自動事件、幀率及計時不會把硬體狀態改成通過。
5. 按「停止紀錄」及「匯出檢查紀錄」。資料僅留本次頁面，重新整理或瀏覽器被關閉會消失，重要階段請先匯出保存。

| 項目 | 操作 | 檢查 |
|---|---|---|
| 藍牙耳機 | 對戰中在耳機與喇叭間來回切換3次 | 沒有重疊配樂、音效補播或應用程式音量增大；中斷後可恢復 |
| 耳機拔插 | 有相容耳機／轉接器時拔插3次 | 同上；沒有器材則維持未測試 |
| 來電 | 有可用來電時中斷對戰，再回到遊戲並繼續 | 通話中不恢復聲音；結束後單份配樂淡入，音量偏好保留 |
| 背景／鎖屏 | 切背景或鎖屏10–30秒，再返回並繼續 | 暫停時間不列入有效對戰，觸控與聲音可正常恢復 |
| 15分鐘熱測 | 另開新紀錄，連續玩到有效對戰滿15分鐘 | 手動觀察發熱、持續卡頓、畫面消失或瀏覽器重載；比較前後每分鐘FPS |

## 紀錄欄位與判讀

- elapsedMs為整段紀錄時間，activeMs只含前景未暫停的對戰畫面；首次／恢復後第一幀不計跨狀態間隔。FPS是實際RAF間隔統計，不是物理引擎120Hz。
- p95FrameMs是向上取整至1ms的95百分位；1000ms以上的桶用p95AtLeast1000Ms標明，避免把更長停頓誤寫成精確1000ms。
- GPU欄位是幾何、貼圖、繪圖程式及單幀呼叫等計數，不是GPU記憶體位元組。不同陀螺／場景數量可以不同，不能只因一次變化就判定洩漏。
- heapBytes是瀏覽器有提供時的近似JS heap；iPhone／Safari可能沒有。網頁無法直接讀取手機溫度，熱測必須人工判斷。
- 音訊紀錄僅含狀態、計數與事件種類，atMs相對頁面時間；沒有錄音、戰績、裝置名稱／識別碼或權杖。不會自動上傳；匯出包含瀏覽器版本與畫面尺寸以便比較。
- 原有音量偏好保留；iPhone系統與耳機本身音量不由網頁控制。

## 自動化方法

- p0-performance.spec.ts：原生WebGL／AudioParam呼叫監測、暫停與旋轉恢復、手機勾選與下載JSON，並檢查沒有戰績內容或自動硬體通過標記。
- p0-soak.spec.ts短期資源測試：同一組模型重建24次，以前12次暖機後比較後12次，隔離初次延遲建立的資源；檢查後續計數是否回到相同水準。
- tests/soak/p0.spec.ts：獨立15分鐘合成特效壓測，約150次換場，涵蓋四種終結、密集撞擊、衝刺與週期音訊恢復，不寫入戰績。每15秒取樣並保留進度，最後以Chrome GC後的JS heap作前後比較。這是桌面測試，不是iPhone熱測或實際15分鐘賽事勝負模擬。

```powershell
npm test
npx playwright test tests/e2e/p0-performance.spec.ts tests/e2e/p0-soak.spec.ts
npx playwright test --config=playwright.soak.config.ts
npm run build
```

15分鐘壓測獨立於一般瀏覽器測試，避免每次操作回歸都必須等待15分鐘。實機驗收表與上述自動化狀態分開紀錄，沒有實機結果時P0實機項目仍未通過。

## 量測依據

- [Three.js官方資源釋放說明](https://threejs.org/manual/pages/how-to-dispose-of-objects.html)：計數包含可重用的內部資源，暖機後觀察重複建立／清理是否穩定，不能把非零計數直接當作洩漏。
- [Chrome官方記憶體診斷](https://developer.chrome.com/docs/devtools/memory-problems)：前後強制GC有助於比較保留的JS heap；JS heap不等同整個分頁、GPU或手機的記憶體。

## 本輪桌面長時間結果

15分鐘測試通過：900.1秒、150次合成換場、58次採樣。暖機後採樣維持89個幾何、5張貼圖、31個繪圖程式；沒有頁面錯誤，聲源、緩衝快取與60筆事件紀錄上限檢查通過。強制GC後的JS heap由8.78MB到10.40MB，約增加1.62MB，通過本輪20MB增量警戒線；這不等於證明所有原生／GPU記憶體都沒有洩漏。

桌面這組合成場景的平均RAF為59.78FPS，不能外推為iPhone幀率或溫度結果。實際戰鬥數值與15–40秒勝負時長不由這個合成壓測驗收。

短期模型資源測試與完整進度、最終報告保留在忽略的artifacts。人工硬體欄位全程維持未測試，沒有將自動化成功轉成實機通過。

實機匯出時請另記手機型號與iOS版本，並保持相同的對戰、畫質與音量條件比較；瀏覽器字串和桌面自動化結果不足以判定特定iPhone已通過。

收尾驗證：P0互動4項及資源重建1項、音訊／演出27項、完整賽事／舊重播／開場／多指15項、WebKit4項通過；另暫停節流案例連跑3次通過。93項核心測試與正式建置通過，獨立程式審查提出的無RAF取樣斷點問題已重現修正。

驗證注意：一輪與建置並行的測試曾發生開場逾時，未取得足夠事件證據確認原因；後續改為序列驗證並連續重跑3次通過，不能據此宣稱所有實機啟動都已驗收。
