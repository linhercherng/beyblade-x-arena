# v0.43.0 P1：診斷保存、發布驗收、各型號觀測

本輪不修改物理引擎5、能力值、戰鬥特性、亂數、計分或戰績格式；v1～v5舊重播沿用原引擎。iPhone、真實耳機與來電仍未驗收。

## 診斷紀錄保存

從「配樂 → 裝置檢查」開始新紀錄。沿用既有更新循環約每5秒保存；開始、停止、人工勾選及切換背景時立即保存。僅保留此網址／瀏覽器的一份草稿，開始新紀錄會取代舊份。

重新開啟後可見保存時間、原版本及經過時間，按「匯出保存紀錄」下載；若保存時仍在量測，明確標示已中止，不自動續錄或將人工項目標成通過。當前檢查與保存快照分開，避免把本次音訊狀態寫入舊紀錄。停止紀錄後可「清除保存紀錄」。

資料僅含原診斷統計、瀏覽器、畫面大小、最近最多60筆音訊事件及人工檢查結果。讀寫皆驗證欄位、型別、有限數值及上限，整份序列化內容最多64KiB（UTF-16）；不含戰績、錄音、耳機名稱或識別碼，不自動上傳。保留原版本與音訊事件的相對頁面時間。

儲存被拒或空間不足時顯示「無法保存」，仍可匯出當前紀錄及正常遊戲。突然當機可能遺失最後一次保存後的資料，瀏覽器清除網站資料或私密模式也不保證持久保存，重要紀錄仍應匯出。

## 統一發布前驗收

先提交來源，再執行：

```powershell
npm run verify:release
```

順序為核心測試 → 全部 Playwright 瀏覽器測試 → 66,708場平衡及型號觀測 → TypeScript檢查／正式建置。瀏覽器命令不加grep或重試，JSON結果不得有略過、失敗或重試通過。不是以先前116項選定案例代替整套。

子程序進度同步顯示於終端並寫入階段日誌。瀏覽器遇第一項失敗即停止；此時整體為失敗、未執行項目不算通過。成功發布仍須完整執行所有案例。

任何階段失敗即停止，未執行階段保留pending，命令回傳非零；每次先覆寫當前狀態，避免沿用舊成功。來源必須已提交，過程中不容許HEAD、已追蹤或未追蹤來源變動（忽略的artifacts與dist除外）。

發布模式禁止重用既有開發伺服器；5178若已被占用就明確失敗，避免測到另一份checkout卻把結果標成目前HEAD。一般開發的Playwright操作仍可沿用現有伺服器。

- 最新摘要：`artifacts/release-verification.json`。
- 每次獨立紀錄：`artifacts/release-verification/<時間>/`，含各階段日誌、完整瀏覽器JSON及摘要。
- 成功摘要包含來源commit、版本、各階段結果、瀏覽器案例數，以及dist每個檔案的SHA-256與大小。
- GitHub push／PR／手動執行使用相同命令，保留`release-verification`和`balance-report` artifact 14天；失敗另存瀏覽器上下文。總工作預算120分鐘供完整套件使用。

CI仍使用軟體GPU profile做功能與資源驗收；不把它當成原生GPU或手機FPS標準。本機原生效能門檻維持原值。15分鐘獨立合成壓測及實機測試仍另列，不冒稱包含在一般發布驗收。

## 各型號平衡觀測

`npm run balance:check`除原報告，另寫：

- `artifacts/balance-observation.md`：91款中文名稱、類型、旋向、樣本數、勝率、得分率與時長表。
- `artifacts/balance-observation.json`：上述資料加玩家位置、對手類型、四種原有發射情境、有向型號配對及終結分布。

觀測直接讀取原allPairs完成的33,124場，不新增對戰，不額外呼叫rng，也不修改Battle。91款每款728次出戰；同型號對戰雙方各計一次，平手列入勝率分母、得分率各半分。有向配對各8次出戰，屬少量樣本，無法據此宣稱某型號必勝。

發射情境沿用歷史全配對的邊界輸入（包含0.4力量輸入），實際處理沿用既有引擎，不冒稱每組都是一般遊玩的標準發射。報告終結計數包含觀測方勝出或落敗，不等同勝出終結數。

型號整體樣本至少200次且勝率落在40～60%之外時列為人工檢查提示，**不阻擋發布、不調數值**。此處等量型號對手與原本等量類型驗收分布不同；原類型40～60%、每場15～40秒及終結比例門檻完全沿用。

## 驗證方法

核心測試涵蓋草稿跨實例／舊版本、損毀與配額拒絕、已中止語意、平手和同型號計數、來源與失敗狀態、未建置產物及瀏覽器略過／重試拒絕。瀏覽器驗證保存、重載、清除、背景快照、定期保存及不可儲存時正常開局；沿用原裝置檢查、完整賽事與v1～v5匯入重播。

完整平衡結果須與v0.42.0報告深度比較相同；發布另外核對同一commit、公開版版本與JS/CSS雜湊。實際通過數以該commit的驗收摘要為準，不預先宣告通過。

首輪完整216項為214通過、2未過，證據留在本機獨立驗收目錄。其一舊MutationObserver把空文字的發射裝飾節點也算成GO文字更新；現只略過純空文字childList，仍記錄相同文字的重複寫入、清除及characterData，並新增同批次兩次GO寫入的自我驗證。另一項觸控診斷案例原本只從專用WebKit設定取得hasTouch，納入一般Chromium完整套件時在首次tap前就失敗；現由案例明確宣告觸控前提，保留原操作與匯出斷言。兩項均不修改產品倒數、音訊或物理。

完整雲端套件也首次涵蓋先前未納入CI的特性、自然終結、衝刺命中與盤體效能頁。首輪取消前的日誌保留畫格不足、未走完模擬、同步操作超時及短暫提示觀測錯過等失敗，沒有當成產品功能已通過。

隔離頁沿用既有精彩重播的雙層驗收方式，新增共用`render-profile.ts`：只有明確的`?software-gpu`才將drawing buffer設為0.25倍並關閉陰影，CSS、鏡頭、模型、零件與物理不變。每份報告列實際GPU、buffer、比例及陰影狀態。原生仍保留原等待與p95<100ms；CI等待實際畫格數或模擬壽命，驗證有限正間隔、同一批幾何／粒子／聲源上限，記錄p95而不宣稱原生FPS。

同步90次暖機在軟體profile仍執行每次Arena.draw，僅略過中間GPU提交、更新world矩陣，finally復原並實際繪圖；新增錯誤也必須復原的測試。頂點邊界改預組合P×V×M，但仍逐網格、逐instance、逐頂點檢查。齒鳴混音案例在CI另明示audio-only，沿用真實Sound與Web Audio，避免短暫duck在GPU阻塞後才取樣；原音量／峰值與前景比例門檻不變，另有實際GPU的衝刺及撞擊案例。

低幀率交戰與GO暫停案例在CI使用640×480，避免把不可控的全尺寸軟體陰影負載疊在刻意的130ms畫格延遲上；原倒數／暫停及對決時鐘門檻不變。低速旋轉的CI分支等待61筆實際旋轉樣本，仍驗證不僵住、每次角差有限且小於2弧度、暫停精確與幾何穩定；報告使用未被dt上限裁短的真實畫格間隔。

診斷另覆蓋同一毫秒內開始／停止的邊界：以DeviceCheck是否建立紀錄判斷可否保存，不把0ms當成未曾記錄，也不將人工停止誤標成中斷。
